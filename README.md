## `aidlc-scale-assessment`

고객이 워크숍·스프린트를 열기 전에 문서 몇 개를 건네고 **"이 기간에 됩니까"** 를 묻는
자리에서 쓴다. 답이 감이 아니라 **문서에서 세어 나온 수**여야 하므로, 기간이 줄어드는
것이 협상이 아니라 계산이 된다.

요건서·전환 계획서·기술 조사서·화면 갭 분석 같은 문서를 **절 단위로 끝까지** 읽고, 두
갈래가 데이터·상태·프로토콜·실패 거동을 서로 합의해야 하는 지점(계약 지점)을 전량 모은다.
요약만 읽으면 잡히지 않는 자리를 특별히 본다 — 범위 제외 절(한쪽이 뺀 것이 다른 쪽의
전제이면 정리됨이 아니라 충돌이다), 한 문서 안의 모순, 여러 갈래에 걸친 완료 기준.

산출물은 **자기완결 단일 HTML 하나**다. 첨부로 혼자 이동하기 때문에, 고객이 파일 하나만
열어도 판정과 근거가 다 보여야 한다.

| 파트 | 묻는 것 |
|---|---|
| 1 · Scale | 무엇이 들어와 있는가 — 갈래 수 · 갈래별 계약 부담 · 확보해야 하는 기존 소스 |
| 2 · What fixes the order | 무엇이 순서를 정하는가 — 층 구조 · 역방향 의존 · 동시 상한 |
| 3 · What must close first | 먼저 닫아야 하는 것 — 계약 지점의 상태 분류 |
| 4 · The N-day scope | 그래서 기간 안에 어디까지 — 역산 · 마지막 날 산출물 · 확인 요청 |

**파트 4가 결론이고**, 앞의 세 파트는 그 결론이 어디서 나왔는지 보여주는 근거다.

파이프라인은 **분석 → 조립 → 독립 검토 → 반영** 이고, 분석 결과를 머리에 담지 않고
파일(`surfaces.json` · `notes.md` · `matrix.md`)로 먼저 떨어뜨린 뒤 조립에 들어간다.
조립은 실패해도 재시도로 복구되지만 분석은 응답이 끊기면 처음부터 다시 읽어야 한다 —
첫 평가에서 세 번의 시도가 모두 그 손실을 봤다. 검토와 반영은 서브에이전트가 맡고,
판정만 런이 한다.

**함께 담긴 검증기** — `term_sweep.py`(문서 간 불일치 후보를 기계로 좁힘) ·
`surface_matrix.py`(계약 지점 수·행렬·인용 하한) · `check_html.py` ·
`check_numbers.py`(본문 수치를 `surfaces.json` 과 대조) · `to_pdf.py`.

발표용 슬라이드가 필요하면 `aidlc-html-deck` 을 쓴다. 이 스킬이 만드는 것은 넘기며 읽는
문서다.

## `aidlc-html-deck`

AI-DLC 발표 덱을 **자기완결 단일 HTML** 로 작성한다. 브라우저에서 화살표 키로 넘긴다.
`.html` 파일이 소스이고 그것을 커밋한다 — 빌드 스크립트도, gitignore 할 생성 산출물도
없다.

그 점이 이 채널이 존재하는 이유다. 클릭으로 단계를 여는 reveal 이 여기서는 `data-step`
속성 하나인데, pptx 덱에서는 애니메이션 슬라이드 하나에 1,628줄짜리 손으로 쓴
`<p:timing>` XML 이 필요했다.

**PDF 경로는 없다**(2026-08-22 폐기 — "PDF 에 대한 고려가 오히려 창의성을 방해한다").
저작과 발표가 모두 브라우저에서 일어나므로 화면에서만 되는 것(클릭으로 도는 explorer,
`<details>`, 은은한 모션)을 마음대로 쓴다. 인쇄를 견뎌야 하는 것이 없다. 그래서 33개
항목 보드의 상세 패널이 클릭으로 바뀌는 섹션 하나가, 전에는 슬라이드 셋이 필요했던
목록을 하나로 담는다.

지키는 것:

- CSS·JS 전부 인라인. 외부 요청은 폰트 CDN 둘뿐. 프레임워크도 빌드 단계도 없다
- **화면에서 흐른다.** 섹션은 `min-height:100vh` 로 문서 흐름 안에서 자란다. 고정
  캔버스에 맞춰 축소하지 않으므로 어떤 프로젝터 비율에서도 꽉 찬다. 화살표 한 번이
  한 화면에 떨어지게 유지한다
- 한국어가 기본 출력 언어. 기울임체 금지 — 강조는 굵게·색·크기
- **모든 슬라이드가 시각 요소를 갖거나, 없는 이유를 밝힌다.** 제목 + 불릿은 생성된
  덱의 실패 양식이다
- 발표자 노트는 `<section>` 의 `data-notes` 에 산문으로. 슬라이드 본문과 같은 공을 들인다
- **직접 본 스크린샷 없이 덱이 끝났다고 말하지 않는다**

워크플로는 **브리프 → 개요에서 멈춤 → 조립 → 검증** 이다. 개요(슬라이드 번호 · 패턴 ·
제목 · 내용 한 줄)를 제시하고 **승인을 기다린다** — 확정되지 않은 구조에 40장의 마크업을
쏟는 것이 이 워크플로의 값비싼 실수다.

**담긴 것** — `assets/deck-base.html`(복사해서 시작하는 골격) ·
`references/design-tokens.md`(색·크기·폰트) · `references/slide-patterns.md`(복붙하는
아홉 가지 원형) · `scripts/deck_screens.py`(섹션 수·섹션별 `<h1>`·스크린샷·텍스트 덤프) ·
`scripts/inline_deck_images.py`(파일을 외부에 넘기기 전 이미지를 base64 로 박음 — 상대
`src` 는 파일이 혼자 이동하면 **조용히 깨진다**).

`.pptx` 덱은 pptx 스킬을 쓴다. 두 경로는 섞이지 않는다.

## `aidlc-v1-git-merge` · `aidlc-v2-git-merge`

여러 개발자가 AI-DLC 프로젝트를 유닛(또는 Bolt)으로 쪼개 병렬로 작업한 뒤 `main` 으로
합칠 때 생기는 충돌을 해소한다. 의도적으로 프로젝트 비의존적이다 — 고정된 폴더 구조를
가정하지 않고 저장소의 실제 배치를 먼저 발견한다. 언어·스택·유닛 배치와 무관하게 쓴다.

먼저 필요한 심상: git 은 **두 브랜치가 같은 파일의 같은 줄**을 고쳤을 때만 충돌을 낸다.
그래서 AI-DLC 병합에는 세 종류의 문제가 생기고, **셋은 위험도가 같지 않다.**

1. **상태 파일**(`aidlc-docs/aidlc-state.md`, `audit.md`) — 손이 아니라 엔진이 쓴다.
   끊임없이 충돌한다. 할 일은 *읽기에* 맞는 텍스트를 만드는 것이 아니라 **엔진이 유효하다고
   받아들이는** 텍스트를 만드는 것이다. 그럴듯해 보이는 손 병합도 상태 기계를 어긋난 채로
   남길 수 있다(체크박스와 맞지 않는 단계 수, 올라가지 않은 버전, 감사 로그와 모순되는
   현재 단계)
2. **공유 코드와 설정** — 텍스트 조정이 아니라 **의도**의 이해가 필요하다
3. **git 이 표시하지 않는 조용한 의미 충돌** — 공유 계약이 한 브랜치에서 바뀌었고 그것을
   쓰는 쪽은 다른 브랜치의 **다른 파일**에 있다. git 은 둘 다 깨끗이 병합하고, 런타임에서
   깨진다. **이것이 가장 위험한 종류다.** 4단계가 이것을 겨냥한다

두 스킬은 **정확히 한 곳에서** 다르다. v2 의 Step 2 는, 병렬 작업이 엔진의 worktree
프리미티브(`aidlc-bolt start --worktree` / `aidlc-bolt complete --merge`)를 썼다면 엔진이
이미 상태 파일을 병합했으므로 손으로 다시 병합하는 것이 오히려 충돌을 **만든다**고 말한다.
v1 에는 호소할 프리미티브가 없다. `references/` 파일은 바이트 단위로 동일하다.

프로젝트는 v1 이거나 v2 이므로 하나만 설치한다.
